No Guest, model, code, evaluator, task result, or artifact was changed by this review. The shared-filesystem line remains frozen.

**Evidence convention.** **DIRECT** = a property stated in a linked primary paper or artifact, or in the existing CoDesk report. **INFERENCE** = a proposed CoDesk mechanism/protocol; it is not an observed CoDesk failure. **UNVERIFIED** = needs a Guest feasibility check. The absence statements below are limited to the inspected sources; they are not claims about every paper in the field.

## Decision in one paragraph

Do **not** add a fifth Core family now. The strongest fresh hypothesis is **spatial-frame / viewport contention**: one goal-directed Actor scrolls or zooms the same still-focused view, invalidating another Actor's earlier screen-coordinate mapping while window, page identity, clipboard, and modal state remain fixed. It deserves a bounded feasibility probe, not an immediate family label. Selection/caret belongs under the existing Application Context candidate; z-order/occlusion belongs under Focus/Modal; notifications belong to interruption exposure; global input-method mode is a plausible but currently high-cost future candidate. Current experimental scope should remain Focus, Clipboard, and the optional Modal/Application Context candidates until these controls are proven.

## Candidate 1 — Spatial-frame / viewport contention

**Recommendation: conditional KEEP as a *feasibility candidate*, not V1 Core.**

- **Hidden state:** scroll offset, zoom/viewport transform, and mapping from a screen coordinate to a task object inside one still-active page or canvas. Window XID, active browser target/page, OS focus, clipboard payload, and modal stack can all remain unchanged. This is **INFERENCE** grounded by OSWorld's geometry sensitivity (§5.2), OSWorld-Noisy's target-window motion (Appendix B.1), and DynamicGUIBench's dynamic lists (§3.2); none of those directly demonstrates two independently scored actors causing it.
- **Collision test:** If a different foreground window or overlay explains the event, classify Focus/Modal. If B switches tab, route, or selected record, classify Application Context. Admit the new family only when the *same page and target identity* remain active and a measured viewport transform alone changes `elementFromPoint(x,y)` or equivalent target mapping.
- **Minimum workflow:** one local, deterministic browser record board with many scrollable rows in one page. Actor A must update record A through the GUI; Actor B must find and update a distant record B, naturally scrolling the board. Their record updates are independent and jointly feasible. An A action planned from an earlier screenshot may hit another row after B scrolls; A must be allowed to observe again and recover. B is never instructed to scroll solely to sabotage A.
- **Controls:** Solo A and Solo B from one seeded board; MA-ID on two independent desktops seeded with the same board and task-relevant state (no cross-Actor record visibility required); MA-SD on one desktop/window. Freeze goals, model/action interface, turn schedule, budgets, evaluator, initial scroll position, and app version. Predefine an exposure window but report whether the relevant B scroll and A stale action actually occurred.
- **Oracle and attribution:** hidden record store checks A and B exact fields plus non-target rows. Instrument read-only window XID/focus, URL/browser target ID, scrollTop/zoom, record IDs at the intended and executed screen points, screenshot/action timing. A mechanism event requires same window/page/focus and a changed coordinate-to-record mapping between A observation and action. End failure alone is insufficient. Recovery requires A to re-observe/reposition and later complete both exact goals.
- **Cost:** medium. A local web board, DOM/record oracle, scroll-offset observer, and one real Guest probe; little new infrastructure. The mechanism is vulnerable to overlap with Application Context, so a failed same-page/constant-focus control should **MERGE** it there.

## Candidate 2 — Selection / caret / active-object ownership

**Recommendation: MERGE into Application Context; do not count a new family.**

- **Hidden state:** active text insertion caret, selected text span, selected table range, or selected canvas object *inside the same app view*. **DIRECT** literature basis: DynamicGUIBench §3.2 explicitly includes recent selection as an ephemeral reference; CUActSpot Appendix C.2 tests cursor placement and span selection. The CoDesk two-Actor conflict is **INFERENCE**.
- **Collision:** Focus/input routing can explain the failure when the active window changes; Clipboard explains a wrong pasted payload; Application Context already covers the active in-app target/object while the OS window is unchanged. If correct window, page, and payload stay fixed but B changes selection, annotate `app_context=selection` rather than inventing family five.
- **Minimum workflow:** A formats a specified paragraph and B edits a different paragraph in one shared Writer/browser-editor document; B's legitimate selection changes the active range before A's pending format command. For a clean MA-ID control, both Guests would need the **same logical document backend**, with independent per-desktop selections; MA-SD would share one editing session. A fresh local file in each MA-ID Guest would change the persistent-document topology and weaken the causal comparison. No shared filesystem is required if a deterministic local web editor/server provides this, but implementing one is significant work.
- **Oracle and attribution:** exact text/style/range/other-paragraph integrity; log active selection and caret location before each actor action and final document deltas. Distinguish wrong selection from wrong window/paste. Both Solo goals and joint feasibility must pass before a shared trial. Recovery is reselecting the intended span and obtaining both exact final states.
- **Cost:** medium-to-high because reliable selection state and equivalent shared-document backend are needed. Existing A-01 (tabs) or an Application Context subtrack is the right home.

## Candidate 3 — Global input-method / keyboard-mode contention

**Recommendation: FUTURE / UNVERIFIED, do not admit to V1.**

- **Hidden state:** OS-wide or session-wide input language/IME, keyboard layout, or overwrite mode that changes how identical key events become text. The WindowsWorld Appendix B.3 observation is **DIRECT** for an IME/keystroke failure in one Windows VM; cross-Actor persistence on the pinned Ubuntu/X11 Guest is **UNVERIFIED**.
- **Collision:** correct window and caret plus wrong character encoding can distinguish this from Focus and Application Context. Clipboard insertion bypasses many keystroke-mode effects, so the actual Qwen3VLAgent action path must be checked before considering this mechanism.
- **Minimum workflow:** Actor A enters exact ASCII identifiers in Calc; Actor B enters a short phrase requiring a different input mode in Writer and leaves that mode active after its legitimate goal. Both must be independently solvable using the *same* action interface and within the fixed budget. MA-ID gives each desktop an independent input mode; MA-SD shares it. A is free to inspect the mode and restore it.
- **Oracle and attribution:** exact saved strings and protected neighboring cells/paragraphs; private trace of active IME/layout, raw submitted GUI key action, committed text, focus, and caret. Failure counts only if mode changed between A observation/action and explains the committed characters while focus/caret were correct. Reverting mode and completing both goals counts recovery.
- **Cost:** high. Requires proving global mode behavior, deterministic reset, Unicode GUI entry, and that the standard agent does not inject text through a path insensitive to the mode. If any Solo fails or the mode is per-window/irrelevant to the action interface, **DROP**.

## Candidate 4 — Notification / interruption ownership

**Recommendation: DROP as a separate family; classify as exposure or Modal/Focus subtype.**

- **Hidden state:** transient notification/toast queue, its anchor/occlusion, and possibly a modal decision owner. **DIRECT** collision: OSWorld-Noisy §4.1 and Appendix B.1 already inject notifications, prompts, and modal overlays; DeskCraft §3.3 has triggered user interruptions; DynamicGUIBench §3.2 has interruptive UI states; OSWorld 2.0 includes mid-task messages.
- **Minimum workflow if used as a control:** A edits Writer; B closes a ticket in a local GUI and the app emits a notification as a legitimate side effect of B's own scored goal. Solo A/B and equivalent MA-ID seeded apps, then MA-SD. The ticket state and Writer ODF are exact oracles; log the toast generation, occlusion region, focus/dialog state, A action, and whether A re-observes. Do not inject a pop-up purely to make A fail.
- **Collision and attribution:** a passive toast with no effect is exposure only; blocking dialog action belongs to Modal; foreground steal/input redirection belongs to Focus. A distinct family would require a remaining state transition after those are controlled, and none is supported by the inspected sources or current CoDesk artifacts.
- **Cost:** low-to-medium for a local ticket app, but no demonstrated family-level gain. Keep as a within-family stressor/annotation, not an independent benchmark track.

## Revisit of prior undo-history proposal

The prior `MECHANISM_EXPANSION_RESEARCH.md` proposed shared Writer undo-history contention. It is genuinely different from Focus/Clipboard if an undo reverts another Actor's completed edit while window/selection are correct. However, an MA-ID run with two separate local documents and an MA-SD run with one shared document would change the **persistent document topology** along with desktop sharing. That violates the task-relevant-state causal contract for this particular workflow. A valid control needs a shared, deterministic collaborative document backend in both conditions, independent desktops for MA-ID, and one shared editing session for MA-SD; no shared filesystem is necessary, but the application/backend engineering cost is high. Therefore keep this as future exploratory work, not a V1 family claim.

## Admission gate and next action

A new family needs (1) independently achievable and jointly feasible A/B goals; (2) equivalent task-relevant initial and persistent state across MA-ID/MA-SD; (3) one directly logged hidden-state variable that differs between conditions; (4) same goal, schedule, budget, agent action path, and exact oracle; (5) evidence that Focus/Clipboard/Modal/Application Context cannot fully explain the event; and (6) separate counts for scheduled exposure, observed interference, outcome, and autonomous recovery.

**Recommended next action:** implement Focus/Clipboard workflows already under way. If capacity allows one bounded new-mechanism probe, test Candidate 1's constant-window/constant-page viewport signature with scripted Actors. A positive signature would justify a full Solo/MA-ID/MA-SD template; a negative or ambiguous signature merges it into Application Context. Do not raise the V1 family count until that gate passes.
