# Case 4 Lite: native Kdenlive repair and real-desktop comparison

Date: 2026-10-30. Branch: `codex/case4-lite`. Model: `gpt-6.1-sol`, medium effort, 15 desktop calls per actor. Provider: user-supplied `https://docode.cc/v1` fallback; the primary endpoint returned timeouts or an upstream 502 during pilot attempts. The provider key is kept outside the repository.

## Why the fixture changed

The original Case 4 MLT writer passed its offline parser tests, but Kdenlive 21.12.3 opened its project with an empty Project Bin and timeline. A visible title bar was therefore insufficient smoke evidence. We created a native project in the real Kdenlive GUI, imported all five synthetic assets, saved it, and reopened it in a fresh KVM Guest. The screenshot is `runs/case4-lite-staged-smoke-20261030a/kdenlive-settled.png`; the smoke status is `NATIVE_PROJECT_WINDOW_VISIBLE`. The private gold project was also saved by Kdenlive after the target timeline edit.

The Lite task repairs an existing 10-second timeline. V1 initially has `clip_01.mp4` at frames 0–74, wrong `clip_04.mp4` at 75–174, and `clip_03.mp4` at 175–249. A correct four-second `clip_02.mp4` is staged on V2 at frames 275–374. A1 has an intact 0–249 music bed. A reviews the source, tells B which clip belongs at 3–7 seconds, and saves `shot_manifest.txt` through the GUI editor while B removes the outtake, moves the staged clip to V1, and saves the native Kdenlive project. The Oracle checks exact timeline tracks and frames, Project Bin contents, profile, media hashes, saved manifest, and A's message. No rendering is required.

## Final-version real-agent runs

All four runs started with the same project SHA-256 `84378805fe02a6ffe21a802d685317978f6fbd595865bf2c925363d2d13836f5` and manifest SHA-256 `a904df7bab3185054a151ceae97ee8ecd549a75f5c4492cad00cec647e66c2b6`. Each used a fresh KVM overlay and the same task, assets, Oracle, model, and collaboration channel. The only experimental change was independent Guests versus one shared Guest; the locked runs additionally serialized each individual desktop action and screenshot.

The independent Guest saved both the corrected native project and manifest. In the ordinary shared run, B saved a correct project, while A's manifest remained `middle_source=UNCONFIRMED`. In the first locked run both remained at their initial state. In the second locked run B saved a correct project but A did not save the manifest; B exhausted the call budget. All 50 actions across the two locked runs record `window_samples_atomic: true`, confirming that the lock serialized individual actions. It did not preserve an actor's application focus across its successive calls. The action traces show Kdenlive and VS Code being restored and focused during interleaved work.

Each run directory contains `pair_pilot_result.json`, `oracle_result.json`, actor action traces, collaboration events, screenshots, initial and final hashes, and ownership cleanup evidence. These are small-sample observations, not a pass-rate estimate or proof that every shared-desktop failure was caused solely by focus contention; model and provider variation remains possible.

## Calibration that shaped the final task

An earlier, simpler variant only asked A to message B and B to repair Kdenlive. It passed independent (`runs/case4-lite-isolated-20261030c`) and action-locked shared (`runs/case4-lite-shared-locked-20261030a`), while ordinary shared failed (`runs/case4-lite-shared-20261030a`). The locked success showed that serializing clicks could resolve that simpler task. The final variant restored A's separate GUI artifact from the original asset-management responsibility and made both actors work in different applications at the same time. The final-version results above are therefore the comparison for this case; the calibration runs must not be pooled with them.
