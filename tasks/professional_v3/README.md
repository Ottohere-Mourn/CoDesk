## 为什么不是简单“多加几项检查”

p1–p3 混合实验中的脚本能批量完成许多 GUI 步骤。v3 保持 GUI、CLI、Python、
应用 API 均可用，把困难放在多源输入理解、专业约束、可编辑原生结构、
跨文件一致性和实际应用中的检查，而非隐藏依赖、禁用工具或压低时间预算。

本次复核 WeaveBench 官网的设计原则，并重读此前缓存的 QGIS、KiCad、
CloudCompare 公开轨迹中的任务、检查项和工具事件，不复述模型思考文本。
可借鉴的是长流程中的不同表示/界面衔接、独立核对原生结果与过程证据；
不能用“要求许多截图”或“规定切换次数”代替真实难度。
QGIS 公开样例也包含实际属性表与地图的联动检查；这启发下面的实时原生验收，
而不是要求完成某个固定鼠标动作。

### 角色兼容性：难而不互相矛盾

- p10 A 读地形和人口，B 读固定道路关闭和需求，不让 B 等 A 的风险结果。
- p11 A 改运动/变换关系，B 改 UV/材质属性；网格拓扑、相机定义和运动包络固定。
  同一对象可以有不同属性所有权；共享材质必须避免影响受保护对象。
- p12 两个 Body 都对接输入中的固定装配基准，不引用另一角色尚未完成的可变参数。
- 各自导出只验收本角色。联合动画/总览由评估器在双方结束后生成，
  不要求一个先结束的角色交付另一个尚未完成的成果。
- 临时选择、活动窗口、当前帧的要求按各自验收时刻判断，不要求最终同时处于
  两个互斥 GUI 状态。最终评分读取同一个共同保存工程。

## 并发问题必须有因果证据

语义目标兼容，不代表读写流程可交错。典型故障是：

1. A、B 都观察/加载版本 v0。
2. A 在当前项目中提交本角色修改，保存为 vA。
3. B 把仍来自 v0 的全量快照保存为 vB，丢掉 A 的修改。
4. 两方都声称完成，但共同文件只能通过一方的目标检查。

这不是让 A/B 写互相冲突的目标，也不是启动后台脚本偷偷毁坏文件。
任务真正的共享写入面是原生文档、图层注册表、数据库、材质引用或参数表。
安全地重读/合并、在活跃文档上做增量修改、短事务、重试和**主动加锁都允许**。
若 agent 自发完全串行化而成功，应记为有效策略，并报告等待时间和实际加速，
不能为了制造低分禁止它。主条件不偷偷增加系统级跨 agent 输入锁。

至少记录以下可观察链条，不能只靠 `mode=parallel` 或总分推断：

| 类型 | 需要的证据 | 单靠什么不能下结论 |
|---|---|---|
| 过期保存/丢更新 | 观察或加载版本、对方已提交的语义差量、后续保存及差量消失 | 同一个文件的修改时间变化 |
| 数据库写冲突 | 提交/重试错误、事务时间、双方表的最终状态 | 某一角色耗时较长 |
| GUI 观察失效 | 实际输入前后的活动窗口/模式/选择，期间对方的操作 | 出现了一张旧截图 |
| 内存与磁盘脱节 | 活跃文档状态、保存版本、导出来源、重新打开的原生状态 | agent 自述“已保存” |
| 导出陈旧 | 当前原生版本与重导入 STEP/GPKG/PDF/渲染的内容差异 | 导出文件存在 |

可信观察器要独立于 agent 的可写报告，记录窗口/进程身份和轻量语义探针；
不得把隐藏参考或评分逻辑放入 agent 容器。原生 UI checkpoint 可以由代码驱动，
但必须真的作用于正在共享的应用，不能用离线图片冒充。自述和隐藏思考过程
不作为成功证据。观察开销需要在所有对照中一致记录，避免探针自己制造锁冲突。

## 单体难度与并发影响分开校准

先保留当前参考预算：每角色 300 动作、90 次成功响应、1500 秒，
`gpt-6-astra / high`、最近 4 张工具图片。不要为了“变难”减少预算。
若实际工程规模需要调整预算，先在开发集定下来并冻结；不能对失败条件临时延长。

开发阶段按单体/顺序表现给任务分层，不预先宣称“等于 WeaveBench”：

- 简单层：成熟脚本或单 agent 在当前预算下稳定完成，留作 sanity/control，不冒充高难题。
- 中高难层：有真实诊断和恢复需求，但能收集到足够的成功顺序样本，适合分析并发损失。
- 极难层：单体也经常失败，作为能力边界单列，不能把接近零分的并发结果归因为共享冲突。

校准集和留出集的输入种子分开；先依 solo/顺序结果冻结难度标签、目标、
评分器和种子列表，再看留出集并发结果。不要挑“恰好并发失败”的样本入榜。
强模型用一个正确脚本完成仍算成功；这提示该样本对 hybrid 不够难，
不是它作弊，也不是应该事后禁止这条解法。

## 验证与准入顺序

1. **资产可行性**：公开单位、容差、拓扑/容量/间隙范围；所有输入为原创合成数据。
   不把缺软件、联网安装失败、损坏到无法修复的工程或无解容量要求当作难度。
2. **独立评分器**：读取真实几何/字段/约束/表达式/原生布局，重开并重新导出。
   路径优化允许等价解；图纸检查原生关联与视觉语义，不匹配特定 SVG 标签或固定句子。
   单纯保留初始对象/文件有效性作为 gate，不再贡献“任务完成进度”分。
3. **正确参考**：pristine、A-only、B-only、A→B、B→A；两个顺序均通过且目标语义一致。
   PDF 时间戳、原生序列化字节、临时焦点和无关图层插入顺序不要求相同。
4. **真实负例**：在新副本中实际制造旧快照覆盖、陈旧导出、损坏参数关联等，
   原生保存、重开，再由评分器检测。只改 inspector JSON 的单元测试不够。
5. **实时观察**：检查所需 live 状态可被真实应用稳定呈现、独立读取；不以肉眼猜成功。
   验证初始/参考工程 GUI 重开、素材可移植、评分与参考不泄露给 agent。
6. **注册新任务**：单独的新 runner/data manifest；旧 p1–p3 的 APPS/批次不被静默替换。
7. **模型校准和冻结**：按下面的匹配条件运行、保留全部尝试，之后才可标为可发布难题。

`critical_checks` 是可追溯业务要求，全部通过才算角色成功；联合成功要求
双方成功且共享工程完整。保留逐项部分分、角色结果和共享 gate 结果，
不把某个截图小瑕疵与工程完全不可用混成一种故障，更不通过增加检查数冒充难度提升。

## 实验矩阵：只生成计划，不启动实验

每个输入实例 × harness 有五个主条件，各自从干净环境开始：

| 条件 | agent 执行数 | 用途 |
|---|---:|---|
| solo A | 1 | A 的单体可解性 |
| solo B | 1 | B 的单体可解性 |
| A→B | 2 | 同桌面顺序共同结果 |
| B→A | 2 | 检查顺序偏置 |
| A∥B，共享桌面 | 2 | 主并发结果 |

先做 p10、两个 harness、一个输入实例：**10 个条件，16 次 agent 执行**。
三对任务、两个 harness、三个匹配输入实例：**90 个条件，144 次 agent 执行**。
这里的三个实例是数据变体，不是对同一输入重复三次采样。若再对每个格子做
三次随机重复，则为 270 个条件、432 次 agent 执行；这是额外预算，未启动。
可选加“隔离桌面双 agent 同时运行”的 API 负载对照，不能把它冒充主并发条件。

在 `CoDesk` 根目录生成第一阶段计划：

```bash
python3 -m tasks.professional_v3.protocol --pairs p10 --repetitions 1 \
  --out runs/research/professional-hard-design-20261103/p10-calibration-plan.json
```

生成器不会连接 VM、调用 API、启动任务，也不会覆盖已有计划；计划中的输入
变体仍需解析到实际资产，`execution_supported=false`，缺少的准入项明确列出。
专用执行器 `experiments.p10_batch` 另行核对作者验证、源文件和输入哈希、
同任务双 agent 预检，并为真实运行绑定输入/提示 manifest 哈希后才执行。
进入校准的前置条件与发布为已校准任务的条件分开，避免把“校准完成”设成
运行首轮校准本身的前置条件；每个输入实例还需绑定真实的冻结 manifest 哈希。
条件顺序在每个匹配块内确定性打乱，harness 顺序随实例轮换，减少固定顺序偏置。

主要报告：两个顺序各自的联合全通过率、并发联合全通过率、逐角色分数、
实际运行重叠、失更新事件、主动锁等待、makespan、tokens/动作通道和重试等待。
单体成功率乘积不是无需假设的联合成功基线。加速应同时报告成功情况，
不能把提前失败的短耗时当成胜利；三实例的小试验不声称统计显著。
429/503、环境启动失败和等待磁盘等另列，保留原始 wall-clock 成绩及受干扰标记，
不静默删掉不利样本，也不把 API 限流误叫任务复杂度或并发冲突。
