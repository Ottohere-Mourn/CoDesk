Version 1.2.x changes only the public paired workflow: after B reports the first live failure, B stages the second query in the browser while A edits the source, then waits for A's saved-revision message before submitting. Version 1.2.1 makes the wait-and-finish obligation explicit after the v1.2.0 pilot ended prematurely. This preserves the same repair, fixture, Oracle, role permissions, model, and desktop-call budget in both topologies. The goal is to test a natural overlap of independent GUI work without injecting a shared-only obstacle. A result will be attributed to focus contention only when the action, active-window, screenshot, and application-event traces support that explanation.

Version 1.2.1 establishes a one-run topology contrast, including a failed shared run after single-call desktop locking. It has not established a success-rate estimate. Its total action count also exceeds Case 1's 10–15-call **combined** target. Version 1.3.0 starts B's browser with Dana and Processing already prepared; this fixture setup is disclosed separately from the model's desktop calls. The first isolated pilot used 14 actual GUI input actions, within the combined target, and 20 tool calls when screenshots and waits are included.

Version 1.3.0 did not satisfy the lock-resistant shared failure target: its lock-enabled shared run passed at A 11 / B 13 calls. Version 1.4.0 keeps the same fixture, Oracle and role instructions but calibrates the paired desktop-call allowance to 12 per actor, leaving two calls of slack above the first isolated run. This budget is identical for isolated, shared and lock-enabled shared trials; their outcomes must all be retained, including any shared pass.

Version 1.4.1 clarifies which collaboration tool to use for the handoff after the invalid v1.4.0 shared trial. The business task, fixture, Oracle and 12-call budget stay unchanged; new paired trials must all use this instruction revision.

Version 1.4.2 keeps the same public task and budget and changes the common pair runner: if A has sent a saved-revision message and B finishes with remaining calls but no final browser event under the current code hash, B is resumed once to complete the requested Apply. The prior trigger required A's message to arrive after B had already exited and missed a near-simultaneous handoff.


Two v1.4.2 model-free setup failures exposed a slow VSCode startup. The pair runner now waits up to 60 three-second checks for the editor file, retries opening the file once if a generic VSCode window is visible, and retains a diagnostic log on timeout. This setup logic is identical in isolated and shared conditions and does not change the task fixture, Oracle, agent budget or instructions. The setup-only check passed before the new paired pilots.

The v1.4.2 paired pilots show the desired contrast in one ordinary shared repeat and one lock-enabled shared trial, both with action-level focus evidence. An earlier ordinary shared run passed under the same version and budget. All outcomes are retained: this small pilot set demonstrates focus contention and its possible impact, but does not establish a stable failure rate or that every simple harness optimization fails.
