# CDD-BV-LITE-001：OrderDesk 组合过滤修复

版本 `1.4.4`。这是 Case 3 的独立 Lite 版本；完整的 `CDD-BV-001` 不变。1.4.3 稳定真实 Guest 的编辑器起始窗口；此版另将候选代码运行异常正确判为验收失败，并保证评估异常后仍执行重置。业务任务和每角色 12 次桌面调用预算不变。

本地合成订单页面已有 8 条公开记录。搜索框按订单号、客户、地区做去空格和大小写无关的包含匹配；状态选择器也必须生效，两者同时设置时取交集。初始 `filtering.py` 在搜索非空时提前返回，忽略状态。浏览器的 Apply、Enter、Clear 和页面布局已经可用，不在本任务修复范围。

A 是开发者，在已打开的 GUI 编辑器中只修改并保存 `filtering.py`。B 是浏览器测试者，已打开的页面中 Dana 与 Processing 已预填但尚未提交：先在搜索框按 Enter 复现，并向 A 报告具体错误；A 收到这一观察后编辑并保存。A 修复期间，B 继续在浏览器中把搜索词改成 `NW-2402`，保留 Processing，但等 A 明确通知最终代码已保存后才点击 Apply 提交。准备好查询后，B 持续查看协作消息并等待，不能在此中间阶段结束任务。页面下次提交会热加载已保存的服务端代码，不必刷新页面。A 发出最终保存通知后不再编辑文件。A/B 同时启动，可读取同一公开订单和需求；B 不编辑文件。任务不提供隐藏 Gold 或 Oracle。

公开预期：`Dana + Processing` 修复后仅显示 `NW-2403`，修复前会错误显示 3 条；`NW-2402 + Processing` 修复后不显示订单；`All` 不限制状态。隐藏 Oracle 检查 B 在初始源码哈希下的真实 Enter 缺陷复现、在最终源码哈希下的真实 Apply 复测，另查组合过滤、状态单筛、`All` 的搜索与空搜索、原始数据和受保护文件、Enter 与 Apply 的事件契约。消息和代码哈希时序另作交接审计；一条消息本身不算业务通过。

目标是 A/B 合计约 10–15 次关键 GUI 调用：A 查看已打开文件、定位缺陷、编辑并保存，B 完成修复前 Enter 复现、并行准备第二组查询及修复后 Apply 检查。已预填的浏览器输入是公开起始状态，两种桌面条件完全相同，且不会自动提交。每角色 12 次桌面调用是模型余量，不是任务目标。正式预算与时限在模型 Pilot 后冻结；不能按条件分别调整。

`single_agent` 使用一个桌面；`collaborative_isolated` 为 A/B 同时运行的两个独立桌面；`collaborative_shared` 为 A/B 同时控制一个桌面。三种条件使用相同订单、代码初态、应用服务、可变项目目录、角色指令、协作接口和 Oracle。Shared 不加入人为干扰；Isolated 不采用串行单 Guest。共享源文件的冲突、应用服务热加载与共享桌面焦点冲突分别记录，只有动作、窗口和截图证据相互印证时才将失败归于焦点。

验证顺序：离线正负控 → 两条件真实 Guest GUI smoke 和重置 → 单 Agent 可解性 → 共享/独立并发 Pilot → 冻结协议后的真实配对。基于实际焦点证据再做对两条件一致的简单 harness 对照。保存所有失败运行，不按结果筛选。
