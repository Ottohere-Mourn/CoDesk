# Multi-Actor Computer Use: overlap matrix

**Audit snapshot:** 2026-09-26. This matrix focuses on GUI/Desktop/Computer-Use work. “Direct collision” requires independent goal-bearing actors, one live desktop/application session, real shared GUI control or same-session state, and evaluation of both goals plus interaction effects. “Partial overlap” means the work shares important GUI/Computer-Use methods or task features but misses one or more of those requirements. “Cross-domain mechanism neighbor” means the work informs concurrency or shared-state evaluation outside GUI Computer Use. Evidence and detailed citations appear in [NOVELTY_AUDIT.md](NOVELTY_AUDIT.md).

## Three-level classification

| Level | Work | Relevant overlap | Audited boundary / evidence | Assessment |
|---|---|---|---|---|
| **Direct collision** | **None located** | — | None of the reviewed papers/artifacts demonstrates independently tasked principals concurrently using the same desktop session and evaluates each principal’s goal plus cross-actor interference. | The candidate gap is bounded to the inspected corpus/search, not a priority claim. |
| **Partial GUI / Computer-Use overlap** | **ParaGUIBench** | Concurrent GUI agents, shared directory, actual concurrent edits to one document, top-level success and efficiency. | Separate Docker desktops explicitly isolate mouse cursor and keyboard focus (paper p. 4); planner decomposes one user task. Appendix A Table XI reports search-and-write shared-doc bottleneck: P=1.47 and SR=10%, paper PDF p. 14 / printed p. 13. Repo `src/stages/run_QA_pipeline_parallel.py`, `src/desktop_env/providers/docker/parallel_manager.py`. | Closest GUI benchmark. Real shared-file interference is occupied; common live desktop/focus and independent goals are not. |
| **Partial GUI / Computer-Use overlap** | **MACU (Multi-Agent Computer Use)** | Parallel screenshot-driven CUA workers evaluated on OSWorld and web computer-use benchmarks; task success and efficiency. | One manager decomposes a single user task into DAG subtasks (paper pp. 1–4); every subagent has an isolated VM (pp. 3–4, appendix p. 14). Repo `run_macu.py`, `utils/macu_runtime.py`, `utils/vm_utils.py`, VM providers. | Direct precedent for multi-agent CUA systems and parallel execution, not same-session actors or benchmarked mutual interference. |
| **Partial GUI / Computer-Use overlap** | **PC-Agent / PC-Eval** | Multiple GUI-oriented agent roles and per-subtask GUI evaluation. | Manager/Progress/Decision/Reflection roles, Decision Agent interacts with GUI (paper §§2.3–3.1, pp. 3–5); one complex instruction decomposed into 79 dependent subtasks across 25 tasks. | Multi-agent GUI architecture, not concurrent independent users sharing input/focus. |
| **Partial GUI / Computer-Use overlap** | **UFO / UFO²** | HostAgent and AppAgents operate on one Windows environment; hybrid GUI/API. | Delegated application subtasks and state transitions among HostAgent/AppAgent; `ufo/agents/states/app_agent_state.py`, `ufo/agents/agent/{host_agent,app_agent}.py`. Evaluated as one requested workflow, no independent competing objectives or interference benchmark. | Same desktop substrate across roles, but hierarchical task decomposition and turn-taking rather than co-actors. |
| **Partial GUI / Computer-Use overlap** | **UFO³ / NebulaBench** | Asynchronous task DAG, device agents, cross-device execution and fault recovery. | Paper reports 55 cross-device tasks over five machines, task/subtask success and injected agent failures (UFO³ paper, arXiv:2511.11332). ParaGUI cites it as closest adjacent work (ParaGUI p. 2–3). | Multi-device collaboration is not one shared desktop session; no focus/input contention evidence. |
| **Partial GUI / Computer-Use overlap** | **MMBench-GUI L4** | “Task Collaboration” label, complex multi-app information transfer, final-state checks. | L4 is one agent coordinating operations among multiple apps (paper §§3.5–3.6, pp. 12–13); example: search conference date, add Calendar event. It finds task success from final state, not multiple actors. | Terminological/task-composition overlap only; not multi-actor collaboration. |
| **Partial GUI / Computer-Use overlap** | **DeskCraft** | GUI + interactive user, request changes, clarification and interruption. | One acting GUI agent plus UserSimulator messages; Kdenlive task `interactive_kdenlive_requirement_change_001` changes horizontal teaser to vertical delivery. Paper pp. 5–8, Appendix H.2 pp. 35–38; task JSON and evaluator at pinned artifact. | Strong GUI+Human interaction precedent, but simulator does not operate the desktop or have an independently scored goal. |
| **Partial GUI / Computer-Use overlap** | **GUIDE** | Human GUI behavior, independent human intention labels, assistance prediction. | Offline screen recordings from human novices; tasks are behavior-state detection, intent prediction and help prediction (paper; project/dataset). The model does not concurrently control the recorded desktop. | Useful for Human Replay intent/task design; no live co-control or interference evaluation. |
| **Partial GUI / Computer-Use overlap** | **OSWorld-Noisy / ENVS** | Real desktop task, controlled disturbances and recovery. | Single task actor under environmental perturbations, not a goal-bearing second principal (paper appendix pp. 13–19). | GUI disturbance control, not multi-actor contention. |
| **Partial GUI / Computer-Use overlap** | **WeaveBench** | GUI and CLI on the same desktop within one trajectory; cross-channel state staleness. | `DOC_task_2_pandoc_docx`, Appendix F.1 PDF p. 34; one agent. | Useful GUI+CLI shared-state contrast, no independent second actor. |
| **Partial GUI / Computer-Use overlap** | **CUA-Universe** | Real desktop applications expose GUI and CLI over one shared application state; stale GUI views are resynchronized after CLI edits. | 160-task CUA-Verse, one agent coordinates modalities in one trajectory (arXiv:2609.05374, §§3–4, pp. 3–6). Parallel exploration agents are data-generation runs on fresh instances. | Strong GUI+CLI state-visibility neighbor; not GUI and CLI as separate active principals. |
| **Partial GUI / Computer-Use overlap** | **WindowsWorld** | GUI benchmark; multi-agent generation/review process; long cross-app tasks. | Agents generate/refine tasks, then one GUI agent performs them; paper arXiv:2604.27776 and repo. | Multi-agent task authoring is not runtime co-action. |
| **Partial GUI / Computer-Use overlap** | **OSWorld-Human** | Human reference trajectories define efficient GUI action paths for OSWorld tasks. | Human trajectories are a comparison/reference for a single acting CUA; no live human-agent co-control (paper arXiv:2506.16042; [artifact](https://github.com/WukLab/osworld-human)). | Relevant to Human Replay traces and action-cost baselines, not an independent human co-actor benchmark. |
| **Cross-domain mechanism neighbor** | **CoAgent** | Independent goals, one live mutable state, stale reads, joint invariant/serializability and recovery. | CLI agents act on one Kubernetes cluster; geo-canary case (paper pp. 1–4), ten workloads/evaluation pp. 9–12. No GUI control. | High-value concurrency/evaluator method precedent; not a GUI benchmark. |
| **Cross-domain mechanism neighbor** | **AgentRoom** | Multiple sessions edit one live shared CRDT filesystem; file claim and semantic conflict. | Concurrent same-line insertions Figure 3 p. 3; common project spec, no individual goal scoring; paper Appendix D pp. 23–24. No GUI. | High-value shared-file and coordination precedent; not a GUI benchmark. |
| **Cross-domain mechanism neighbor** | **CooperBench** | Distinct feature goals, solo tests and composed patch compatibility. | Separate worker workspaces by default; optional shared Git server (`git_enabled=False` default); paper pp. 3–7 and repo evaluator. | Good independent/joint success design; no live shared desktop. |
| **Cross-domain mechanism neighbor** | **STALE** | Solo-valid task pair, composition-induced failure, message recovery. | Offline patch composition with union tests; corrected `real_corrected.jsonl` and constructed real-Django helper tier; paper pp. 1–5 incl. Appendix C. | Strong causal attribution method; no GUI runtime topology. |
| **Cross-domain mechanism neighbor** | **SWE-Touch** | External code edit changes an active agent’s shared workspace. | A synthesized user counter-edit is injected into one coding agent’s repo; paired task success; no GUI actor or second independent goal. Repo runtime/schema. | Workspace freshness precedent only. |
| **Cross-domain mechanism neighbor** | **CodeCRDT** | Concurrent edits to one shared code document and semantic conflict analysis. | Coding/editor-system study, six tasks; paper pp. 1–9. | Shared-state editing mechanism, not a computer-use benchmark. |

## Task-branch view

| V0 branch | Closest GUI-side overlap | Cross-domain mechanism neighbors | Current positioning |
|---|---|---|---|
| **GUI + GUI** | ParaGUIBench; MACU; PC-Agent; UFO/UFO² | AgentRoom and CoAgent clarify shared-resource consistency designs | Distinguish independent actor goals and one shared screen/focus/pointer/keyboard route from decomposed parallel subagents, isolated VMs, and role-based turn-taking. Test window focus, input routing, clipboard and app state, then jointly score both goals. |
| **GUI + CLI** | WeaveBench and CUA-Universe cover one actor choosing/interleaving GUI and CLI; CUA-Universe explicitly synchronizes GUI view after CLI edits | CoAgent; AgentRoom; CooperBench; STALE | Keep as a distinct actor-pair task. GUI-visible state/cache and CLI writes should interact in the same live app/session; compare GUI-only, CLI-only, serialized and concurrent controls. A plain shared CSV is an auxiliary mechanism case. |
| **GUI + Human** | DeskCraft; GUIDE; OSWorld-Human reference trajectories | SWE-Touch is a code-workspace intervention analogue | Give the human a separately satisfiable intention and real pointer/keyboard actions. A scripted interruption message or prerecorded trace without an independent goal is not a co-actor condition. |

## Evaluation overlap and remaining difference

| Capability | Existing coverage | What V0 should measure |
|---|---|---|
| Aggregate GUI task success / efficiency | ParaGUIBench, MACU | Preserve as baseline outcomes; not the novelty by itself. |
| Same-document concurrent GUI edits | ParaGUIBench | Use as an auxiliary shared-file condition; report each actor’s task plus document invariants and conflict/recovery. |
| GUI focus/window/input competition | No direct benchmark found in inspected set; ParaGUIBench explicitly prevents it with isolated desktops | Instrument active window, focus owner, pointer and keyboard route; attribute misdirected actions and assess recovery. |
| Independent actor goals + joint GUI state | CoAgent / CooperBench / STALE offer analogous designs in non-GUI environments | Define solo-valid goals, a jointly satisfiable state, and hidden joint invariants for each GUI task. |
| GUI+Human interaction | DeskCraft message simulator; GUIDE observes recorded humans | Evaluate two active principals’ separate goals and actions in one shared session. |
| GUI+CLI state staleness | WeaveBench for one actor; CUA-Universe for one hybrid actor | Establish that different principals have distinct channels and stale/updated observations affect their UI actions. |
| LLM-free success oracle | Several relevant GUI works use executable final-state checks; CLI precedents use tests/invariants | Keep hidden programmatic state predicates as the success oracle; use LLMs only for task/trace review if needed. |

## Conclusion

There is no direct collision in this audit, but there are meaningful partial GUI/Computer-Use overlaps. The most important are ParaGUIBench’s shared-file editing across isolated desktops, MACU’s parallel isolated-VM GUI workers, and DeskCraft’s simulated human instruction changes. Retain GUI+GUI, GUI+CLI and GUI+Human. Make the claimed contribution the evaluation of distinct actors sharing GUI-specific live control/state, not the broad idea of multi-agent work or shared files alone.
